# Cloudflare persistence staging

This is a staged D1 port. Authentication and selected team callers now use explicit Cloudflare imports; the canonical `@cap/database` entrypoint still selects MySQL while other caller groups are being ported. This intermediate source state must not be deployed as a working application or run against mixed production databases. Complete the remaining callers and verify the affected flows before the coordinated canonical cutover.

## Implemented and verified

The generated initial migration contains all 49 upstream tables, 502 columns, 128 indexes (including unique indexes), 12 foreign keys, and nine nonnegative checks for upstream unsigned counters. The schema retains relation exports, branded identifier types, JSON shapes, enum types, defaults, generated creation dates, and foreign-key actions.

- Dates are stored as Unix milliseconds and returned as `Date` values. Database-generated current timestamps use seconds multiplied by 1,000; explicit application dates retain milliseconds.
- JSON is stored as text and decoded by Drizzle. Booleans use Drizzle integer/boolean mapping. Integer byte counters retain values above 32 bits; callers still must stay within JavaScript's safe integer range.
- Index names have table prefixes because SQLite's index namespace is database-wide.
- The MySQL storage-object prefix index is non-unique. The SQLite equivalent indexes the complete `objectKey`, which supports exact and prefix-range lookups without MySQL's text-index prefix restriction. No unique prefix index exists in this upstream schema. Drizzle Kit 0.31 generated invalid SQL for the attempted expression index, so the source uses a normal full-key index; generated SQL was not manually edited.
- Email fields use `COLLATE NOCASE`. Tests verify ASCII case-insensitive account lookup and uniqueness, including viewer grants.
- `createCloudflareDb(binding)` uses the supplied D1 binding without a process-global cache. Interactive `transaction()` calls fail before invoking their callback; ported callers must use D1 atomic `batch()` operations or conditional statements.
- The generated `0001_d1_concurrency` migration adds a database revision and 147 mutation triggers across all 49 application tables. Inserts, updates, deletes, and foreign-key cascades participate in conflict detection. Its SQL is generated by `generate-concurrency-migration.ts`; the custom migration and snapshot were created with Drizzle Kit.
- D1 counts trigger changes in its native `meta.changes`. The adapter executes an additional `SELECT changes()` in the same batch after each mutation to report only directly affected rows. Zero-row claims remain zero and one-row claims remain one. This deliberately adds query overhead; `rows_written` still reflects the actual database work.
- The generated `0002_d1_validation` migration adds 98 BEFORE INSERT/UPDATE triggers without rebuilding tables or replacing revision triggers. It derives the 502-column contract from the existing MySQL `migrations/meta/0051_snapshot.json`, whose table and SQL-type mapping was verified against the original source. Varchar limits count Unicode characters, including embedded NUL; TEXT/LONGTEXT enforce their byte ceilings. Raw JSON must be valid JSON, booleans must be 0/1, integers keep their source signed/unsigned ranges, bigint values fit JavaScript safe integers, and floats stay finite within the source float range. Dates remain integer Unix milliseconds within JavaScript's representable Date range. TypeScript-only varchar enum annotations are not promoted into database enum constraints.

## Shared caller contract

Keep normal SQLite Drizzle selects and single conditional mutations. Use `.onConflictDoUpdate({ target, set })` with the actual unique key, `.returning()` when a mutation must return rows, and `result.meta.changes` for affected rows through `createCloudflareDb`. Replace each MySQL JSON/date expression deliberately. No SQL text rewriting or interactive transaction emulation is provided.

For read-dependent changes, import `atomic` from `@cap/database/cloudflare/atomic`:

```typescript
const result = await atomic(database, async (snapshot) => {
	const [row] = await snapshot.read((reader) =>
		reader.select().from(table).where(eq(table.id, id)),
	);
	if (!row) return { statements: [], result: false };
	return {
		statements: [
			database.update(table).set({ value: row.value + 1 }).where(eq(table.id, id)),
		],
		result: true,
	};
});
```

`atomic<T>(database, planner, { maxAttempts?: number }): Promise<T>` brackets the planner's reads with a monotonically increasing revision, then checks that same revision inside the committing D1 batch using a named CHECK constraint. A conflict rolls back the complete batch and retries the planner. Only confirmed snapshot conflicts retry; transport errors and other constraint failures propagate because a lost response may follow a successful commit. Callers that need safe request replay must persist an idempotency receipt in the same batch.

The planner receives only `snapshot.read(reader => ...)`, whose reader exposes `select`, `selectDistinct`, and `query`. It returns `AtomicPlan<T>`, containing lazy `AtomicStatement[]` and a result. All reads must be awaited. Do not execute writes, network requests, emails, storage operations, or queue dispatch inside a planner: it may run again. Construct stable IDs and timestamps before planning. Do not await the returned statements. Return only after their batch commits. A business error thrown during an inconsistent snapshot is retried; an error against an unchanged snapshot propagates.

Existing callbacks that read after writing must be rewritten explicitly: calculate the projected row in the planner, use set-based SQL such as `INSERT ... SELECT`, or read the committed result afterward. Helpers accepting a MySQL transaction must become read helpers or statement builders. Ownership, membership, leases, version predicates, counters, and idempotency checks remain part of the plan; they must not be discarded when removing `.for("update")`.

The initial fence is database-wide. This deliberately favors correctness for the team's workload and can cause conflicts between unrelated writes. Default retry limit is eight, with bounded jitter; exhaustion throws `AtomicConflictError`. The private bridge allows 100 physical statements per request, so an atomic plan may contain at most 48 application statements after guards and mutation-count queries. Use bounded set-based operations for larger changes; never split an atomic invariant across unrelated batches. Long-running transfers/deletes should use durable resumable operations with their own recorded progress.

## Private container bridge

`@cap/database/cloudflare/bridge` exports:

- `createD1BridgeBinding({ url?, fetch? })`, returning the D1 binding surface consumed by Drizzle. Default URL is `http://cap.database/query`.
- `handleD1BridgeRequest(request, binding)`, which executes prepared statements and atomic batches through the supplied native D1 binding.

The runtime must mount this handler exclusively on the container's private `outboundByHost` virtual hostname. It is a database capability, not a public application API; the handler itself does not authenticate public callers. No public Worker route may forward to it. Requests validate operation shapes, parameter types, query lengths, statement counts, and a 1 MiB body limit. Binary parameters preserve byte values; raw rows preserve positional mapping for Drizzle joins. Redirects, arbitrary exec, dump, and sessions are unavailable. Reads use the native primary binding. Neither transport nor SQL text is automatically retried or rewritten.

Apply migrations through controlled deployment tooling before using the primitive. Request handling never creates tables or triggers. After adding an application table, generate and review a new migration with its three revision triggers; do not edit an already-applied historical migration. The initial generator's `--check` verifies its reproducible output against the current 49-table source.

## Identity and team access

`@cap/database/auth/identity` supplies the canonical `normalizeEmail` used by the ported authentication and invitation paths. It trims surrounding whitespace, normalizes the local part to Unicode NFC and lowercase, converts the domain through IDNA to lowercase ASCII, and rejects control/format characters and invalid labels. Local parts are limited to 64 UTF-8 bytes and complete addresses to 255 UTF-8 bytes. Accents remain significant: this deliberately does not emulate MySQL accent-insensitive collation. Existing or imported identities must be normalized and checked for collisions before being accepted; all viewer-grant and import writers must use this same policy.

`CAP_RUNTIME=cloudflare` and `DATABASE_PROVIDER=d1` are required by the lazy application accessor. `CAP_OWNER_EMAIL` identifies the exact bootstrap owner, defaulting to the approved team owner. `CAP_INVITE_ONLY=false` is rejected. New accounts require an unexpired pending invitation to an active organization, or the exact owner address. A provisioned but unverified membership cannot bypass an expired or revoked invitation. Established members need a verified email or linked account, and a live organization. Domain-wide automatic signup is not enabled. Cloudflare Pro entitlement remains deployment-wide and does not require a Stripe subscription.

`requireActiveOrganization`, `requireOrganizationMember`, and `requireOrganizationManager` in `@cap/database/cloudflare/access` run inside an atomic snapshot. The owner is derived from `organizations.ownerId`; a membership row cannot grant itself ownership. Organization deletion first marks the organization and fences recording attempts before external media cleanup. The final metadata cleanup uses bounded set-based statements and repairs user organization pointers atomically. Automatic resumption of interrupted external cleanup remains a runtime workflow responsibility.

The Node 24 test suite runs generated migrations in an isolated Miniflare D1 database and disposes it afterward. It checks every upstream table/column shape and index, nullable uniqueness, composite keys, date/JSON/boolean round trips, generated dates, foreign-key rejection and cascade, large counters, and atomic rollback when a batch fails. It does not use production data or credentials.

## Remaining cutover blockers

1. SQLite `NOCASE` handles ASCII case only. The explicit identity policy above handles Unicode normalization and IDNA; all remaining grant/import callers must use it, and any existing data must pass collision reconciliation. Other text columns use SQLite binary collation unless a caller applies an explicit normalization policy. This is not an emulation of MySQL accent-insensitive collation.
2. Field lengths, JSON syntax, numeric bounds, and logical booleans are now enforced by `0002_d1_validation`, including direct raw SQL writes. Run the generated `validation-preflight.sql` before applying it and require every `invalid_rows` count to be zero. Domain-level object shapes and authorization still belong to application validation. These triggers have passed local D1 tests but must be applied through the controlled migration process before application cutover.
3. MySQL `ON UPDATE CURRENT_TIMESTAMP` becomes Drizzle `$onUpdate`. Updates through this adapter receive the timestamp, but raw SQL updates must explicitly set it. SQLite has no matching automatic column clause. Audit all raw writes and imports.
4. D1 does not support the existing interactive transaction and `SELECT ... FOR UPDATE` model. Do not replace transactions with unrelated statements. Redesign conditional claims, counters, quotas, idempotency, ownership transfers, and read-dependent writes with equivalent atomicity and concurrency tests.
5. Replace MySQL upserts, result-array/`affectedRows` assumptions, MySQL date/JSON/string functions, auth adapters, and Effect MySQL services. Native MySQL drivers must not enter the Worker runtime. D1 parameter, query-size, transaction, and result limits need workload-specific checks.
6. Generated custom creation dates are verified for ISO dates with or without milliseconds and invalid/missing-date fallback. Reconcile legacy metadata formats and timezone assumptions during import; SQLite's date parser is not a full emulation of MySQL `STR_TO_DATE`.
7. Authentication/team callers are being ported explicitly; other caller groups and the canonical entrypoint still require coordinated cutover. Production authentication, the new concurrency migration, backup/restore, and end-to-end desktop flows have not been deployed or verified by the local persistence tests.


Migration generation requires no database credentials. Apply through Wrangler's D1 migration commands only to the explicitly selected deployment database after reviewing the generated artifacts. This package never automatically migrates a database at request startup.

From repository root, inspect existing data before applying the validation migration:

```powershell
node scripts/cloudflare/validation-preflight.mjs
```

The preflight is read-only and uses authenticated Wrangler. It verifies all 49 table results, reports invalid-row counts, and exits unsuccessfully when any invalid rows exist. Migration `0002` is generated from the committed original MySQL snapshot so it remains reproducible after the canonical schema module switches to D1.
